# Read-only MongoDB / Cloudinary reconciliation

Run `npm run reconcile:media -- --out /tmp/earn-media-reconciliation.json` from the backend. The output file must not already exist. Without `--out`, stdout includes summary counts and affected model/record IDs for issues, with no media URLs or credentials.

The command loads backend/.env (existing process environment takes precedence), connects to the configured MongoDB database, and uses only native-driver listCollections/find reads. It never imports application models, creates indexes, connects to R2, uploads, deletes, or changes database/provider configuration. Cloudinary access is authenticated Admin API GET only. No source file bytes are downloaded. Output files are local, mode 0600.

Coverage: User avatars and creator links; Post images/videos/documents/thumbnails and legacy comment attachment fields; Story media/thumbnails; Task video/thumbnail/social links (including creator tasks); TaskSubmission proof; CreatorCoinRequest payment proof; Media primary objects and renditions. There is no Message model and current Post comments are text-only. Legacy messages/comments collections are checked if present. Other models have no direct media fields; WatchSession.videoId is a hash of task playback identity, not a Cloudinary public ID. Reads include inactive records and surviving expired records, with no application filtering.

Cloudinary identity is resource type + delivery type + public ID, checked against the configured account. Raw public IDs retain their extension. Image/video delivery extensions and supported URL transformations/signatures are removed; URLs and signatures never appear in output. Same-record URL and embedded metadata identifying one asset are coalesced. Additional records referencing that identity count as duplicates; duplicates are informational. Unknown/malformed identities and cross-account Cloudinary URLs require review. Explicit R2 references/application content links are reported separately; R2 object existence is not checked.

Cloudinary inventory includes paginated image/video/raw assets with upload/private/authenticated delivery. Missing inventory matches receive individual authenticated metadata GETs: only 404 means missing; authorization, network, and API errors abort the reconciliation. Inventory metadata establishes asset ID, resource type, version, size and available format, not original-byte checksum or end-user delivery accessibility. Embedded metadata mismatches require review. Unreferenced inventory assets are informational, not automatically erroneous.

Counts: DB media references are logical record/identity references, including separately classified external/local and R2 references. Existing/missing counts are reference counts; referenced bytes count unique resolved Cloudinary assets once. Duplicate count includes missing identities used by multiple records. The report contains safe affected model/record IDs and field paths. Cross-service inventory and MongoDB majority reads are not a single atomic snapshot; reconcile again near any separately authorized migration.

Exit 0 means reconciliation completed, even when missing/malformed references exist. Exit 1 means it did not complete (configuration, metadata API, DB, or report-output failure). Readiness is distinct from exit status. An empty database cannot validate another database's references: always inspect databaseName, coverage and databaseScopeWarning before interpreting readiness.

Validation on 2026-09-29: configured database `earn_task_platform_staging`; all seven media-bearing collections existed but contained zero records. Cloudinary inventory: 358 assets / 611,243,220 bytes. All 358 assets are unreferenced relative to this empty staging database. Production references were not inspected. No migration was run. The focused tests cover identities, missing versus API failure, duplicate accounting, metadata mismatches, redaction, and GET-only Cloudinary requests.

## Environment and migration eligibility safeguards

Readiness uses the effective `NODE_ENV`: production reports PRODUCTION, staging reports STAGING, and an absent/unrecognized environment requires review. A clean reconciliation with references reports readiness for **migration review**, not permission to execute. Zero resolved Cloudinary references reports `NO REFERENCED CLOUDINARY ASSETS — NO MIGRATION CANDIDATES`, even when the Cloudinary inventory is nonempty. `referencedCloudinaryAssets` counts unique resolved assets; `referencesWithExistingSource` counts logical database references.

`migrate-media.js` now obtains fresh read-only reconciliation using the same configured database and Cloudinary inventory. Database configuration is therefore required even for its dry-run. Inventory membership alone is never migration eligibility: only resolved, referenced asset IDs with matching version, bytes, resource type and delivery type enter the existing source validation and destination-conflict checks. Missing sources, malformed references and metadata mismatches block planning. Unreferenced assets are reported as `unreferenced_not_authorized`; they are not copied. The dry-run separates `referencedAssets`, `unreferencedAssets`, `eligible`, and eligible `estimatedBytes`. No journal, source download, database write, or provider mutation occurs in dry-run.

Execution safeguards also apply to programmatic `run` calls before any journal access. Production requires an explicit `--confirm-production` acknowledgment **and remains disabled in this validation phase even with that acknowledgment**. This change does not enable production migration. Existing staging/test bucket, source-prefix, execution opt-in, bucket confirmation and journal safeguards remain in force. Reconciliation reads are not an atomic cross-service snapshot and do not independently establish that a deployment is production.

## Evidence binding and runtime authority

Migration evidence is issued only by a fresh `collect(..., {forMigration:true})` in the current process. A private registry recognizes the issued report object; copied/serialized reports cannot mint evidence. The report, inventory and bound target are frozen. Each issuance has a unique generation ID and SHA-256 fingerprints binding its references, inventory (including immutable IDs, public IDs, types, versions, sizes and source URLs), and target. Target binding covers `NODE_ENV`, the explicit database name and exact configured MongoDB target, Cloudinary account/prefix/credential identity, effective R2 provider/account/bucket/endpoint/region/private-mode/credential identity, and destination-key scheme. Credentials are never included in reports; only combined fingerprints are emitted.

Evidence is single-use, expires five minutes after collection starts, and is checked against actual process configuration before candidate selection, destination reads, and uploads. Resuming requires fresh reconciliation; old journals do not grant eligibility. Journal scope includes the target, inventory and reference fingerprints, so changes require review rather than silently reusing the old journal. Timestamp validation alone is insufficient: missing, modified, cached or cross-target evidence is rejected by the issuance and binding checks. This protects the supported CLI and module entry points, not against arbitrary malicious code executing inside the same Node process.

`run()` no longer accepts source, provider, environment, Cloudinary-account or copy-function overrides. It constructs its R2 provider from actual runtime configuration and consumes the sealed inventory. Source prefix and download URL identity must agree with the reconciled asset before destination inspection. Production execution remains disabled regardless of confirmation flags. Dry-run enforces the same target/private-mode validation without journal creation, content downloads, uploads or deletes. Tests mock native MongoDB reads, Cloudinary inventory, and R2 operations; no real database/storage writes are necessary for these regression tests. Reconciliation remains a bounded-age read snapshot, not an atomic lock across MongoDB and Cloudinary.

## Running isolated tests

- `npm run test:media-safety`: migration/reconciliation tests install a process-local guard that blocks real MongoDB connections, network sockets, fetch, credential-file loading, and non-Node child processes. Tests explicitly mock the required reads and provider operations. CLI regression child processes load the same guard. Temporary local fixture/journal files are allowed; database and provider writes are not.
- `npm test`: the complete backend suite. Node's default test-file process isolation confines the media guard to those test files. Ordinary API tests retain the existing disposable MongoDB harness: temporary data directory, loopback-only random port, and `earn_isolated_test` database, with teardown. They never use the application's configured MongoDB URI. No production migration guard is disabled or changed by either command.

Do not apply a suite-wide MongoDB-blocking preload to the ordinary API tests: it prevents their explicitly disposable database setup. The scoped media guard is loaded by the test files themselves, so it also applies when those files are run directly.
